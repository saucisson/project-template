# feat(N3): the staging and release deployment channels (ADR-0008)

- Date: 2026-11-25
- Type: feature (CI workflow and documentation); no constitutional file touched, no product code, N3 already records the trigger contract
- Scope: .github/workflows/deploy.yml (new), docs/deployment.md (new)
- Motive: N3 makes the merge itself the deploy trigger and the staging deployment the substrate of the morning verification package; the template had no deployment workflow at all, so the daily-to-staging and main-to-release distinction existed only as prose in the engineering rules
- Evidence: the workflow triggers on push of daily and main only, selects the channel from the branch name, publishes to the GitHub environment of the same name so the two channels stay separable in protection rules and deployment history, and reads one secrets set per channel (STAGING_* and RELEASE_*: SSH key, host, user); the remote command is deliberately a connection smoke (`ssh ... "true"`), because a repository instantiated from the template has no product code yet, and docs/deployment.md carries the instance contract: replace the smoke with the real distribution (rsync, OCI image, remote build) and record the choice in the instance ADR, the N8 per-repo implementation principle; the docs also pin the staging side of N3 (staging stays equal to daily, candidate flags live there only, the validation console sends the owner there) and the rollback rule (redeploy the previous environment SHA)
- Known limits: the template ships no distribution step, so the workflow cannot deploy anything real until an instance fills it in; the YAML triggers of the workflow are the only mechanical front here (no lint covers YAML), reviewed by eye; the current staging target (the OVH VPS) is named in the docs but its coordinates live in the repository secrets only, never in the tree
